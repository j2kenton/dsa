# Release checklist

- Run `npm run build`, `npm test`, and `npm run test:chrome`. The Chrome command validates the generated ZIP's production manifest, then loads a fixture-only unpacked copy with its two fixture origins added solely because CDP cannot grant the transient `activeTab` permission a real user gesture provides. It checks trusted-context content-script isolation, dynamic injection on a genuinely non-LeetCode host, the worker storage gate, panel handshake, worker-restart rehydration of an interrupted request, the side-panel open probe, a `coach:close-panel` → `window.close()` self-close probe on a real extension document, and a full extension-reload open probe. In headless mode the side-panel open probe is inconclusive; if the smoke log prints the inconclusive banner, re-run in a headful desktop session (`DSA_SMOKE_HEADFUL=1`) and confirm the open probe (and the close probe, if it also printed inconclusive) passes. The close probe only proves `window.close()` closes an extension document loaded via `page.goto()` — it is not a substitute for the native side-panel click-through below, since a real docked side panel isn't opened the same way.
- Load the unpacked `extension/` directory in Chrome 116+ and verify trusted-context persistent storage, session-only storage, Save & Test, update, and deletion.
- Side-panel open gate: click the extension icon (or "Coach me" context menu) and confirm the panel opens on the first click. The panel is enabled by default (Option A), so no retry or pre-enable should be needed. After the panel opens, confirm it follows the active tab in that window (Chrome's built-in side-panel behavior).
- **Extension-reload first-click gate (Option A):**
  1. Open `https://leetcode.com/problems/two-sum/` and verify one click opens the panel.
  2. Go to `chrome://extensions`, find Algo Coach, and click the reload (↻) button.
  3. Wait for the extension to finish reloading (the service worker starts automatically).
  4. Click the extension icon again on the same LeetCode problem tab. The panel must open on the first click without any badge error or retry prompt.
  5. If the panel does not open, inspect the service-worker console for `[coach] Unexpected sidePanel.open() failure:` entries. Copy the exact error message and add it to the appropriate `KNOWN_*_SIGNATURES` array in `extension/background.js`, then re-test.
- **Error-signature capture for the exact-match classifier:** If a real-Chrome `sidePanel.open()` failure occurs that does not match the existing `KNOWN_DISABLED_SIGNATURES` or `KNOWN_ACCESS_DENIED_SIGNATURES` arrays, the unexpected path logs the raw error to the service-worker console via `console.warn("[coach] Unexpected sidePanel.open() failure:", <message>, "(tab:", <id>, <url>, ")")`. Open the service-worker DevTools console, locate the logged message, and verify the exact error string. Add the lowercased `.message` value to the correct array. The comparison uses strict `===` equality on the lowercased message string — a substring match is not sufficient.
- In two separate Chrome windows, open a coach session in each and confirm that each side panel follows only its own window/tab.
- **Action-icon toggle gate:** with the panel closed, click the toolbar icon and confirm it opens and launches/resumes coaching for the active tab. Click the icon again and confirm the panel closes (via `window.close()` from `coach:close-panel`) with no badge error and no new session created. Click a third time and confirm it reopens with the same confirmed session's history intact. Close the panel with its own built-in X button instead, then confirm the next icon click opens it (state stays in sync via `panelPorts` disconnect handling). Repeat the open/close toggle with two Chrome windows open and confirm toggling in one window never opens or closes the other's panel. Finally, confirm right-click → "Start coaching" always opens the panel and never closes it. `npm run test:chrome` now automatically proves `window.close()` self-closes a real extension document in response to `coach:close-panel`, but it exercises a `page.goto()`-loaded document, not a docked native side panel — this manual click-through remains the only check that the *native* docked panel closes and reopens correctly. Record the exact Chrome version tested here in the release notes.
- Confirm a LeetCode capture, then verify the selected-text fallback on another page and template insertion on both a LeetCode and non-LeetCode editor.
- Kill the extension service worker while a provider request is pending; reconnect the panel and use Retry without recapturing.
- Verify the toolbar and context-menu coach launch surfaces by hand. The keyboard command is intentionally not shipped: the Phase 0 d1 tab-delivery spike did not establish a dependable command target.
- With a dedicated spend-capped OpenAI test key, run Save & Test by hand from the loaded options page and confirm the authenticated round trip succeeds, then delete the key. Record only the sanitized fields — date, Chrome version, provider endpoint, pass/fail — in `docs/decisions/0001-provider-byok.md`. No automated suite accepts a real key; do not record the key, request headers, or problem text anywhere.
- Confirm `store-assets/privacy-policy.md` still matches what the extension actually transmits, in particular the "Attach my editor code" flow: with the checkbox off, inspect the outbound provider request in service-worker DevTools and confirm no editor contents are present; with it on, confirm the editor's current contents are present for that turn only and are absent from `chrome.storage.session` afterward. Also open a coach session on a non-LeetCode page and confirm the checkbox itself renders disabled and unchecked, since the worker's `canReadEditor` gate is what the checkbox state reflects.
- On a file longer than one screen, the "with checkbox on" check above only sees the scrolled-into-view lines (`readEditorCode` reads the rendered `.view-lines` DOM, not the full Monaco buffer) — before checking the outbound request, scroll the LeetCode editor to the part you're asking about first, mirroring the panel's own "Best-effort read of the visible editor…" copy.
- From an active coaching session on a LeetCode problem page, navigate (same tab) to a non-`/problems/` LeetCode page (e.g. Discuss) and confirm the "Attach my editor code" checkbox becomes disabled — `session.url` now tracks that tab's live location rather than the URL captured when coaching started.
